<h3 style="color: crimson; font-family: 'Press Start 2P', 'system-ui'">x86: Non-optimizing MSVC</h3>

<p>
Let us compile:
</p>

<!-- 🧠 Code Block Component -->
<div class="code-box" data-lang="Assembly" style="border:1px solid #30363d;border-radius:8px;overflow:hidden;background:#0d1117;font-family:Consolas, monospace;">
  <pre style="margin:0;padding:1rem;font-size:15px;line-height:1.6;overflow-x:auto;color:#c9d1d9;">
<code>
_eos$ = -4                               ; local variable eos
_str$ = 8                                ; parameter str
_strlen PROC
    push    ebp
    mov     ebp, esp
    push    ecx                          ; allocate space for eos

    mov     eax, DWORD PTR _str$[ebp]    ; load pointer to string into EAX
    mov     DWORD PTR _eos$[ebp], eax     ; store in eos

$LN2@strlen_:
    mov     ecx, DWORD PTR _eos$[ebp]    ; ECX = eos

    ; load 8-bit byte from address in ECX and sign-extend to 32-bit into EDX
    movsx   edx, BYTE PTR [ecx]

    mov     eax, DWORD PTR _eos$[ebp]    ; EAX = eos
    add     eax, 1                       ; increment EAX
    mov     DWORD PTR _eos$[ebp], eax    ; store back to eos

    test    edx, edx                     ; is EDX zero?
    je      SHORT $LN1@strlen_           ; yes, exit loop

    jmp     SHORT $LN2@strlen_           ; continue loop

$LN1@strlen_:
    ; calculate difference between pointers
    mov     eax, DWORD PTR _eos$[ebp]
    sub     eax, DWORD PTR _str$[ebp]
    sub     eax, 1                       ; subtract 1 and return result

    mov     esp, ebp
    pop     ebp
    ret     0
_strlen ENDP
</code>
  </pre>
</div>

<p>
We encountered two new instructions here: <code style="color: chartreuse;">MOVSX</code> and <code style="color: chartreuse;">TEST</code>.
</p>
<p>
The first — <code style="color: chartreuse;">MOVSX</code> — takes a byte from a memory address and stores the value in a 32-bit register.
</p>
<p>
<code style="color: chartreuse;">MOVSX</code> means MOV with Sign-Extend.
</p>
<p>
<code style="color: chartreuse;">MOVSX</code> sets the rest of the bits, from bit 8 to bit 31, to 1 if the loaded byte was negative, or to 0 if positive. This is the reason.
</p>
<p>
By default, the <code style="color: chartreuse;">char</code> type is signed in MSVC and GCC.
</p>
<p>
If we have two values, one of type <code style="color: chartreuse;">char</code> and the other of type <code style="color: chartreuse;">int</code> (also signed), and the first contains -2 (represented as 0xFE), and we simply copy this byte into <code style="color: chartreuse;">int</code>, it will become 0x000000FE, which from the perspective of signed <code style="color: chartreuse;">int</code> equals 254, not -2. In signed <code style="color: chartreuse;">int</code>, -2 is represented as 0xFFFFFFFE.
</p>
<p>
So if we need to transfer 0xFE from a variable of type <code style="color: chartreuse;">char</code> to a variable of type <code style="color: chartreuse;">int</code>, we need to identify its sign and extend it.
</p>
<p>
This is what <code style="color: chartreuse;">MOVSX</code> does. It is hard to say whether the compiler needed to place the <code style="color: chartreuse;">char</code> variable in EDX; it could have taken just the 8-bit part of the register (like DL). It is obvious that the register allocator in the compiler works this way.
</p>
<p>
Then we see <code style="color: chartreuse;">TEST EDX, EDX</code>. You can read more about the <code style="color: chartreuse;">TEST</code> 
</p>
<p>
Here this instruction simply checks whether the value in EDX equals zero or not.
</p>

<p>
The result is almost the same as in MSVC, but here we see <code style="color: chartreuse;">MOVZX</code> instead of <code style="color: chartreuse;">MOVSX</code>.
</p>
<p>
<code style="color: chartreuse;">MOVZX</code> means MOV with Zero-Extend.
</p>
<p>
This instruction copies an 8-bit or 16-bit value into a 32-bit register and sets the rest of the bits to 0.
</p>
<p>
In fact, this instruction is useful only to replace a pair of instructions like this:
</p>

<code>
xor eax, eax
mov al, [...]
</code>
  </pre>
</div>

<p>
On the other hand, it is obvious that the compiler could generate code like this:
</p>

<!-- 🧠 Code Block Component -->
<div class="code-box" data-lang="Assembly" style="border:1px solid #30363d;border-radius:8px;overflow:hidden;background:#0d1117;font-family:Consolas, monospace;">

<code>

test al, al
</code>
  </pre>
</div>

<p>
This is almost the same thing, but the upper bits in the EAX register would contain random noise.
</p>
<p>
The author said this is a flaw in the compiler — it is unable to generate clearer code. Honestly, the compiler is not obligated to generate code understandable to humans at all.
</p>
<p>
The new instruction for us next is <code style="color: chartreuse;">SETNZ</code>.
</p>
<p>
Here, if AL is not zero, <code style="color: chartreuse;">test al, al</code> sets the ZF flag to 0, but <code style="color: chartreuse;">SETNZ</code>, if ZF==0 (NZ means not zero), sets AL = 1.
</p>
<p>
In simple terms, if AL is not zero, jump to <code style="color: chartreuse;">loc_80483F0</code>.
</p>
<p>
The compiler generated somewhat redundant code, but let us not forget that optimizations are turned off.
</p>

<h3 style="color: crimson; font-family: 'Press Start 2P', 'system-ui'">Optimizing MSVC</h3>

<p>
Now let us compile all this in MSVC 2012 with optimizations turned on (/Ox):
</p>

<!-- 🧠 Code Block Component -->
<div class="code-box" data-lang="Assembly" style="border:1px solid #30363d;border-radius:8px;overflow:hidden;background:#0d1117;font-family:Consolas, monospace;">
  <pre style="margin:0;padding:1rem;font-size:15px;line-height:1.6;overflow-x:auto;color:#c9d1d9;">
<code>
_str$ = 8
_strlen PROC
    mov     edx, DWORD PTR _str$[esp-4]  ; EDX = pointer to string
    mov     eax, edx                     ; EAX = EDX (copy pointer)

$LL2@strlen:
    mov     cl, BYTE PTR [eax]           ; CL = current byte
    inc     eax                          ; increment pointer
    test    cl, cl                       ; is current byte zero?
    jne     SHORT $LL2@strlen            ; no, continue loop

    ret     0

</code>

<p>
Now everything is simpler.
</p>
<p>
No need to say that the compiler can use registers with such efficiency only in small functions with few local variables.
</p>
<p>
<code style="color: chartreuse;">INC/DEC</code> are increment/decrement instructions, meaning in other words: add or subtract 1 from a variable.
</p>

<h3 style="color: crimson; font-family: 'Press Start 2P', 'system-ui'">ARM: 32-bit ARM</h3>

<h3 style="color: crimson; font-family: 'Press Start 2P', 'system-ui'">Non-optimizing Xcode 4.6.3 (LLVM) (ARM mode)</h3>

<!-- 🧠 Code Block Component -->
<div class="code-box" data-lang="Assembly" style="border:1px solid #30363d;border-radius:8px;overflow:hidden;background:#0d1117;font-family:Consolas, monospace;">
  <pre style="margin:0;padding:1rem;font-size:15px;line-height:1.6;overflow-x:auto;color:#c9d1d9;">
<code>
_strlen
eos = -8
str = -4

    SUB     SP, SP, #8                   ; allocate 8 bytes for locals
    STR     R0, [SP,#8+str]              ; store input pointer in str
    LDR     R0, [SP,#8+str]
    STR     R0, [SP,#8+eos]              ; copy to eos

loc_2CB8:                                    ; loop body start
    LDR     R0, [SP,#8+eos]              ; load eos
    ADD     R1, R0, #1                   ; increment
    STR     R1, [SP,#8+eos]              ; store back
    LDRSB   R0, [R0]                     ; load signed byte and sign-extend
    CMP     R0, #0
    BEQ     loc_2CD4                     ; exit if zero
    B       loc_2CB8                     ; continue loop

loc_2CD4:
    LDR     R0, [SP,#8+eos]              ; load eos
    LDR     R1, [SP,#8+str]              ; load str
    SUB     R0, R0, R1                   ; R0 = eos - str
    SUB     R0, R0, #1                   ; R0 -= 1
    ADD     SP, SP, #8                   ; deallocate
    BX      LR                           ; return
</code>
  </pre>
</div>

<p>
Non-optimizing LLVM generates a lot of redundant code, but here we can see how the function works with local variables on the stack.
</p>
<p>
There are only two local variables in our function: eos and str. In this listing from IDA, we manually renamed var_8 and var_4 to eos and str.
</p>
<p>
The first instructions simply save the input value in both str and eos.
</p>
<p>
The loop body starts at label loc_2CB8.
</p>
<p>
The first 3 instructions in the loop body (LDR, ADD, STR) load the value of eos into R0. Then the value is incremented and stored back in eos on the stack.
</p>
<p>
The next instruction <code style="color: chartreuse;">LDRSB R0, [R0]</code> ("Load Register Signed Byte") loads a byte from memory at the address in R0 and sign-extends it to 32-bit. This is similar to the <code style="color: chartreuse;">MOVSX</code> instruction in x86.
</p>
<p>
The compiler treats this byte as signed because the <code style="color: chartreuse;">char</code> type is signed according to the C standard. This was written about before regarding x86.
</p>
<p>
It must be said that it is impossible to use an 8-bit or 16-bit part of a 32-bit register in ARM separately from the whole register, as is done in x86.
</p>
<p>
It is obvious that this is because x86 has a huge history of backward compatibility with its ancestors down to 16-bit 8086 and even 8-bit 8080, but ARM was created from scratch as a 32-bit RISC processor.
</p>
<p>
Therefore, to process individual bytes in ARM, 32-bit registers must still be used.
</p>
<p>
So <code style="color: chartreuse;">LDRSB</code> loads bytes from the string into R0 one by one.
</p>
<p>
The following <code style="color: chartreuse;">CMP</code> and <code style="color: chartreuse;">BEQ</code> instructions check whether the loaded byte equals 0 or not.
</p>
<p>
If not 0, control returns to the beginning of the loop body. If 0, the loop ends.
</p>
<p>
At the end of the function, the difference between eos and str is calculated, 1 is subtracted from it, and the resulting value is returned via R0.
</p>
<p>
Note: no registers are saved in this function.
</p>
<p>
This is because in the ARM calling convention, registers R0-R3 are called "scratch registers", designed for passing arguments, and we are not required to restore their values when the function ends, because the calling function will not use them again. Therefore, we can use them for anything we want.
</p>
<p>
No other registers were used here, so nothing is saved on the stack.
</p>
<p>
Therefore, control can return to the calling function with a simple jump (BX) to the address in the LR register.
</p>

<h3 style="color: crimson; font-family: 'Press Start 2P', 'system-ui'">Optimizing Xcode 4.6.3 (LLVM) (Thumb mode)</h3>

<!-- 🧠 Code Block Component -->
<div class="code-box" data-lang="Assembly" style="border:1px solid #30363d;border-radius:8px;overflow:hidden;background:#0d1117;font-family:Consolas, monospace;">
  <pre style="margin:0;padding:1rem;font-size:15px;line-height:1.6;overflow-x:auto;color:#c9d1d9;">
<code>
_strlen
    MOV     R1, R0                       ; R1 = input pointer (eos)

loc_2DF6:
    LDRB.W  R2, [R1],#1                  ; load byte and increment R1
    CMP     R2, #0
    BNE     loc_2DF6                     ; continue if not zero
    MVNS    R0, R0                       ; invert bits (like NOT)
    ADD     R0, R1                       ; R0 = R1 + R0
    BX      LR                           ; return
</code>
  </pre>
</div>

<p>
As optimizing LLVM concluded, eos and str do not need stack space and can always be in registers.
</p>
<p>
Before the loop body starts, str is always in R0, and eos in R1.
</p>
<p>
The instruction <code style="color: chartreuse;">LDRB.W R2, [R1],#1</code> loads a byte from memory at the address in R1 into R2, and sign-extends it to a 32-bit value, but not only that.
</p>
<p>
The #1 at the end of the instruction means "Post-indexed addressing", meaning 1 will be added to R1 after the byte is loaded. 
</p>
<p>
Then we see <code style="color: chartreuse;">CMP</code> and <code style="color: chartreuse;">BNE</code> in the loop body, these instructions continue the loop until a 0 is found in the string.
</p>
<p>
<code style="color: chartreuse;">MVNS</code> (inverts all bits, like NOT in x86) and the <code style="color: chartreuse;">ADD</code> instruction calculate eos − str − 1.
</p>
<p>
In fact, these instructions calculate R0 = str + eos, which is functionally equivalent to what was in the source code
</p>
<p>
It is obvious that LLVM, like GCC, concluded that this code can be shorter (or faster).
</p>

<h3 style="color: crimson; font-family: 'Press Start 2P', 'system-ui'">Optimizing Keil 6/2013 (ARM mode)</h3>

<div class="code-box" data-lang="Assembly" style="border:1px solid #30363d;border-radius:8px;overflow:hidden;background:#0d1117;font-family:Consolas, monospace;">
  <pre style="margin:0;padding:1rem;font-size:15px;line-height:1.6;overflow-x:auto;color:#c9d1d9;">
<code>
_strlen
    MOV     R1, R0                       ; R1 = input pointer (eos)

loc_2C8:
    LDRB    R2, [R1],#1                  ; load byte and increment R1
    CMP     R2, #0
    SUBEQ   R0, R1, R0                   ; if zero, R0 = R1 - R0
    SUBEQ   R0, R0, #1                   ; R0 -= 1
    BNE     loc_2C8                      ; continue if not zero
    BX      LR                           ; return
</code>
  </pre>
</div>

<p>
Almost the same as what we saw before, with the difference that the expression str − eos − 1 can be calculated not at the end of the function, but inside the loop body itself.
</p>
<p>
The suffix -EQ as we remember means that the instruction executes only if the operands in the previous <code style="color: chartreuse;">CMP</code> were equal.
</p>
<p>
Thus, if R0 contains 0, the two <code style="color: chartreuse;">SUBEQ</code> instructions execute and the result remains in register R0.
</p>

    or      $at, $zero                   ; NOP (delay slot)

<p>
MIPS has no NOT instruction, but it has NOR which is OR + NOT.
</p>
<p>
This operation is used a lot in digital electronics.
</p>
<p>
For example, the Apollo Guidance Computer used in the Apollo program was built using only 5600 NOR gates.
</p>
<p>
But the NOR element is not very popular in computer programming.
</p>
<p>
Therefore, the NOT operation is implemented here as: NOR DST, $ZERO, SRC
</p>
<p>
(Inverting the bits of a signed number is the same as changing its sign and subtracting 1 from the result.)
</p>
<p>
So what NOT does here is take the value of str and turn it into −str − 1.
</p>
<p>
The following addition operation prepares the result.
</p>
