<p>
Note something: <b>MSVC</b> generates Assembly code using the <b>Intel syntax</b>,  
and we’ll explain the difference between it and <b>AT&amp;T syntax</b> later.
</p>

<p>
The compiler produces a file called <code>1.obj</code>, which is later linked to create <code>1.exe</code>.
</p>

<p>
That file contains several sections:
</p>

<ul>
  <li><code><b style = "color: #db8f1e;">CONST</b></code> → for constant data (like strings).</li>
  <li><code><b style = "color: #db8f1e;">_TEXT</b></code> → for the code itself.</li>
</ul>

<p>
The string <code>"hello, world"</code> in C/C++ is of type <code>const char[]</code>,  
but since it doesn’t have an explicit name, the compiler gives it an internal name like <code>$SG3830</code>.
</p>

<p>
So we can write the code like this:
</p>



```c/c++
#include <stdio.h>
const char $SG3830[] = "hello, world\n";

int main()
{
    printf($SG3830);
    return 0;
}
```

<p>
If we look again at the Assembly, we’ll notice the string ends with a small byte <b>(0)</b>,  
and that’s normal for C/C++ strings.
</p>

<h2 style="color:#3ba2a6;"><b>Analyzing the Assembly code</b></h2>

<h3>1. <code><b style = "color: #fd0d68">CONST SEGMENT</b></code></h3>

<p>
This part contains <b>constant data</b> (like the texts inside the program).
</p>

<p>
The computer stores the sentence <code>"hello, world"</code> here,  
and gives it an internal name so the compiler can access it later.
</p>


```assembly
$SG3830 DB 'hello, world', 0AH, 00H
```

<ul>
  <li><code>$SG3830</code> → is the name chosen by the compiler.</li>
  <li><code>DB</code> means “Define Bytes”, i.e., store bytes.</li>
  <li><code>'hello, world'</code> → the actual text.</li>
  <li><code>0AH</code> = newline code <code>\n</code>.</li>
  <li><code>00H</code> = zero byte marking “end of string”.</li>
</ul>

<h3>2. <code><b style = "color: #fd0d68">PUBLIC _main</b></code></h3>

<p>
This means there’s a function named <code>main</code> that will be public (available to the whole program).
</p>

<h3>3. <code><b style = "color: #fd0d68">EXTRN _printf:PROC</b></code></h3>

<p>
This means there’s an external function called <code>printf</code>  
that’s not written here but will come from another library (the C standard library).
</p>

<p>
After that comes the <code>_TEXT SEGMENT</code> part —  
this is where the <b>actual executable code</b> resides.
</p>

<hr>

<h3><code><b style = "color: #fd0d68">_main PROC</b></code></h3>

<p>
This marks the beginning of the <code>main()</code> function.
</p>

<h3><code><b style = "color: #fd0d68">push ebp</b></code></h3>

<p>
This is the first line in almost any function.  
The computer saves the old value of <b>ebp</b> (the base pointer) to return to it later.
</p>

<h3><code><b style = "color: #fd0d68">mov ebp, esp</b></code></h3>

<p>
Here we say:  
“Make the base pointer (<b>ebp</b>) point to the same place as the stack pointer (<b>esp</b>).”
</p>

<p>
That means we’ve started a “new frame” on the stack for this function’s work.
</p>

<h3><code> <b style = "color: #fd0d68">push OFFSET $SG3830 </b></code></h3>

<p>
Here we push the <b>address of the string "hello, world"</b> onto the stack.
</p>

<p>
After <code>printf()</code> finishes and returns,  
the address we pushed is still on the stack — but we no longer need it,  
so we fix the stack pointer by:
</p>



```assembly
ADD ESP, 4
```

<p>
Why 4?  
Because the program is 32-bit, and an address takes exactly 4 bytes.  
If it were 64-bit, we’d need 8 bytes.
</p>

<p>
The instruction:
</p>


```assembly
ADD ESP, 4
```


<p>
is almost the same as:
</p>


```assembly
POP register
```

<p>
but without actually using a register.
</p>

<p>
Some compilers (like Intel C++ Compiler) prefer:
</p>


```assembly
POP ECX
```
<p>
to make the code smaller (1 byte instead of 3).
</p>

<p>
Example from Oracle RDBMS code:
</p>



```assembly
.text:0800029A  push ebx
.text:0800029B  call qksfroChild
.text:080002A0  pop  ecx
```

<p>
Even MSVC can do that sometimes:
</p>



```assembly
.text:0102106F  push 0
.text:01021071  call ds:time
.text:01021077  pop ecx
```

<hr>

<p>
After calling <code>printf()</code>, the original C/C++ code has <code>return 0;</code>
</p>

<p>
In Assembly, that turns into:
</p>

```assembly
XOR EAX, EAX
```

<p>
The word <b>XOR</b> means “Exclusive OR”,  
but the compiler uses it instead of <code>MOV EAX, 0</code> because the code becomes shorter (2 bytes instead of 5).
</p>

<p>
Out of curiosity, I wanted to know why <code>XOR EAX, EAX</code> is shorter than <code>MOV EAX, 0</code>.  
Turns out the reason is simple — when encoded in x86 machine code:
</p>



```assembly
31 C0
```

<p>
That’s only 2 bytes.
</p>

<p>
While <code>MOV EAX, 0</code> becomes:
</p>



```assembly
B8 00 00 00 00
```

<p>
That’s 5 bytes in total (1 + 4).
</p>

<p>
This was just something extra I wanted to understand better,  
so I decided to write it down as well.
</p>

<p>
Some other compilers use:
</p>


```assembly
SUB EAX, EAX
```

<p>
which means “subtract EAX from itself” → result is also zero.
</p>

<hr>

<p>
Finally:
</p>

<pre style="background:#0d1117;padding:1rem;border-radius:8px;color:#c9d1d9;">RET</pre>



<p>
This returns control to the program that called <code>main()</code>  
(usually the C runtime code), which then returns back to the operating system.
</p>

<hr>



<h2 style="color:#9a3ba6;"><b>GCC</b></h2>

<p>
Now let’s try compiling the same C/C++ “Hello, world” code,  
but this time using <b>GCC</b> on a <b>Linux</b> system, with this command:
</p>

```terminal
gcc 1.c -o 1
```

<p>
Then we’ll use a program called <b>IDA Disassembler</b> to see how the function <code>main()</code>  
was built after compilation.  
IDA uses the same <b>Intel-syntax</b> style as MSVC.
</p>



```assembly
main                 proc near
var_10              = dword ptr -10h

    push    ebp
    mov     ebp, esp
    and     esp, 0FFFFFFF0h
    sub     esp, 10h
    mov     eax, offset aHelloWorld ; "hello, world\n"
    mov     [esp+10h+var_10], eax
    call    _printf
    mov     eax, 0
    leave
    retn
endp main
```

<p>
The result is almost identical to the code generated by MSVC.  
The address of the string <b>"hello, world"</b> (stored in the <code>.data</code> section)  
is first loaded into the <b>EAX</b> register, then stored on the stack.
</p>

<p>
Also, at the beginning of the function, there’s this line:
</p>



```assembly
AND ESP, 0FFFFFFF0h
```

<p>
Here, GCC performs something called <b>stack alignment</b>.
</p>

<p>
That means it ensures that the address of <b>ESP</b> is a multiple of 16  
(i.e., ends with 0 or 0x0).
</p>

<p>
Why?  
Because the CPU reads memory in “blocks,” and  
if a block starts at a neatly aligned address (like 0x1000 instead of 0x1003),  
it’s much faster.
</p>

<p>
So this line aligns the stack for better performance.
</p>

<p>
Then we have this line:
</p>



```assembly
SUB ESP, 10h
```

<p>
This allocates 16 bytes on the stack (since 10h = 16).  
In reality, we only need 4 bytes,  
but the compiler reserves 16 to maintain proper alignment.
</p>

<p>
After that, the address of the string is stored on the stack directly  
without using <code>PUSH</code>.
</p>

<p>
The variable <code>var_10</code> is a local variable,  
and it’s also used as the argument to the <code>printf()</code> function.
</p>

<p>
Then the function <code>printf()</code> is called.
</p>

<p>
When GCC is running without <b>optimization</b>, it uses:
</p>



```assembly
MOV EAX, 0
```

<p>
instead of shorter instructions like <code>XOR EAX, EAX</code>.
</p>

<p>
The last instruction <code>LEAVE</code> is equivalent to:
</p>




```assembly
MOV ESP, EBP
POP EBP
```
<p>
This restores the stack to its original state and  
recovers the previous <b>EBP</b> value that existed before the function started.
</p>

<hr>

<h2 style="color:#3ba2a6;"><b>GCC: AT&amp;T syntax</b></h2>

<p>
Now let’s see how this code looks when written in <b>AT&amp;T syntax</b>.  
This style is more common on UNIX systems.
</p>



```terminal
cc -S 1_1.c
```

<p>
This command tells GCC to generate Assembly code instead of an executable file.
</p>

<p>Here’s the generated code:</p>



```assembly
.file "1_1.c"
.section .rodata
.LC0:
    .string "hello, world\n"
.text
.globl main
.type main, @function
main:
.LFB0:
    .cfi_startproc
    pushl %ebp
    .cfi_def_cfa_offset 8
    .cfi_offset 5, -8
    movl %esp, %ebp
    .cfi_def_cfa_register 5
    andl $-16, %esp
    subl $16, %esp
    movl $.LC0, (%esp)
    call printf
    movl $0, %eax
    leave
    ret
    .cfi_endproc
.LFE0:
.size main, .-main
.ident "GCC: (Ubuntu/Linaro 4.7.3-1ubuntu1) 4.7.3"
.section .note.GNU-stack,"",@progbits
```

<p>
The code contains many directives starting with a dot (<code>.</code>).  
These are called <b>macros</b>, and we don’t need to worry about them now.  
We can safely ignore them — except for <code>.string</code>,  
because it’s what stores the text <code>"hello, world\n"</code> in memory as a <b>C-string</b> (ending with null).
</p>

<p>
After removing unnecessary lines, the simplified version looks like this:
</p>



```assembly
.LC0:
    .string "hello, world\n"
main:
    pushl   %ebp
    mov     %esp, %ebp
    andl    $-16, %esp
    subl    $16, %esp
    movl    $.LC0, (%esp)
    call    printf
    movl    $0, %eax
    leave
    ret
```

<hr>

<h2 style="color:#3ba2a6;"><b>Differences between Intel and AT&amp;T syntax</b></h2>

<p>
<b style = "color: #c75a21">1-</b>  The order of <b>source</b> and <b>destination</b> is reversed:
</p>

<ul>
  <li>Intel: <code> <b style = "color: #37e36b;">&lt;instruction&gt; &lt;destination&gt;, &lt;source&gt;</b></code></li>
  <li>AT&amp;T: <code><b style = "color: #37e36b;">&lt;instruction&gt; &lt;source&gt;, &lt;destination&gt;</b></code></li>
</ul>

<p>
So, in Intel:
</p>

<pre style="background:#0d1117;padding:1rem;border-radius:8px;color:#c9d1d9;">mov eax, ebx</pre>

<p>
In AT&amp;T, it becomes:
</p>

<pre style="background:#0d1117;padding:1rem;border-radius:8px;color:#c9d1d9;">movl %ebx, %eax</pre>

<p>
To remember:  
Think of Intel like an “equals sign (=)”  
and AT&amp;T like an “arrow →”, meaning the value moves from left to right.
</p>

<hr>

<p>
<b style = "color: #c75a21">2 -</b>  In AT&amp;T:
</p>

<ul>
  <li>Registers start with <b>%</b> (e.g., <code>%eax</code>).</li>
  <li>Constants start with <b>$</b> (e.g., <code>$16</code>).</li>
  <li>Parentheses <b>( )</b> are used instead of square brackets <b>[ ]</b>.</li>
</ul>

<hr>

<p>
<b style = "color: #c75a21">3 -</b>  AT&amp;T also adds a letter at the end of each instruction to indicate data size:
</p>

<ul>
  <li><b style = "color: #37e36b;">q</b> → quad (64-bit)</li>
  <li><b style = "color: #37e36b;">l</b> → long (32-bit)</li>
  <li><b style = "color: #37e36b;">w</b> → word (16-bit)</li>
  <li><b style = "color: #37e36b;">b</b> → byte (8-bit)</li>
</ul>

<hr>

<h3>Back to our code:</h3>

<p>
The generated code looks very similar to what IDA produces,  
but there’s a small difference:
</p>

<p>
The value <code>0FFFFFFF0h</code> appears here as <code>$-16</code>.  
They’re actually the same:
</p>

<ul>
  <li>In decimal: -16</li>
  <li>In hexadecimal: 0xFFFFFFF0</li>
</ul>

<p>
Both represent the same number in 32-bit systems.
</p>

<hr>

<p>
Another note:  
The return value is set using <code>MOV</code> instead of <code>XOR</code>.
</p>

<p>
So we see:
</p>

<pre style="background:#0d1117;padding:1rem;border-radius:8px;color:#c9d1d9;">movl $0, %eax</pre>

<p>
This copies the value 0 into <code>%eax</code>.  
The word “move” is a bit misleading — it doesn’t move, it <b>copies</b>.  
In other architectures, you’ll find similar instructions called “LOAD” or “STORE”.
</p>

<h2 style="color:#9a3ba6;"><b>String patching (Win32)</b></h2>

<p>
We can easily locate the string “hello, world” inside the executable file.  
It looks something like this:
</p>




```hex dump
h  e  l  l  o  ,     w  o  r  l  d  \n  \0
68 65 6C 6C 6F 2C 20 77 6F 72 6C 64 0A 00
```


<p>
If we wanted to translate it into Spanish, it would look like:
</p>



```hex dump
h  o  l  a  \n  \0
68 6F 6C 61 0A 00
```

<p>
The original string length is 14 bytes (like in the example above),  
and the new string is 6 bytes long.  
You can replace it directly and leave the remaining bytes as-is,  
or pad them with <code>00</code> until the space is filled. Example after modification:
</p>


```hex dump
68 6F 6C 61 0A 00 00 00 00 00 00 00 00 00
```
<p>
If we wanted to insert a longer message,  
there might be some null bytes (<code>00</code>) after the original English text.  
It’s not always safe to overwrite them — they might be used by CRT code.  
So only do it if you know what you’re doing.
</p>

<p>
The author shared a real story about software cracking:
</p>

<p>
There was an image-processing program that, when unregistered,  
would add watermarks like:  
“This image was processed by the evaluation version of [Program Name]”.
</p>

<p>
By coincidence, they found this string inside the executable,  
and replaced it with spaces — the watermark disappeared!  
Technically, the program was still adding the watermark,  
but the text became invisible.
</p>

<h2 style="color:#3ba2a6;"><b>Software localization in the MS-DOS era</b></h2>

<p>
This method was common for translating MS-DOS programs into Russian  
during the 1980s and 1990s.  
It was suitable even for people unfamiliar with machine code or executable file formats.
</p>

<p>
The new text couldn’t be longer than the original,  
because adding bytes might overwrite nearby code or data.  
Russian words were often longer,  
so translated versions had many abbreviations to make text fit.
</p>

<p>
The same might have happened for other languages too.  
And with <b>Delphi strings</b>, the string length field also had to be updated if needed.
</p>

<h1 style="color:#9a3ba6;"><b>1.6 x86-64</b></h1>

<hr>

<p>
Now we compile this time using <b>64-bit MSVC</b>:
</p>

```assembly
$SG2989 DB  'hello, world', 0AH, 00H

main PROC
    sub     rsp, 40
    lea     rcx, OFFSET FLAT:$SG2989
    call    printf
    xor     eax, eax
    add     rsp, 40
    ret     0
main ENDP
```

<p>
In <b>x86-64</b> all registers were extended to <b>64-bit</b>, and their names now start with <b>R</b>.
</p>

<p>
To reduce stack usage (i.e., avoid repeated memory/cache access) there is a common convention to pass function <b>arguments</b> in registers rather than on the stack — commonly called <b>fastcall</b>.
</p>

<p>
That means some arguments are passed in registers, and the rest (if any) go on the stack.
</p>

<p>
On <b>Win64</b>, the first four arguments of any function are passed in these registers:
</p>

<ul>
  <li><b style = "color: #37e36b;">RCX</b></li>
  <li><b style = "color: #37e36b;">RDX</b></li>
  <li><b style = "color: #37e36b;">R8</b></li>
  <li><b style = "color: #37e36b;">R9</b></li>
</ul>

<p>
That’s what we see here: the pointer to the string passed to <code>printf()</code> is now passed in <b>RCX</b> instead of being pushed on the stack.
</p>

<p>
Also, pointers are now 64-bit, so they are passed in the 64-bit registers (the ones starting with <b>R-</b>).
</p>

<p>
For backward compatibility you can still access the lower 32-bit part via the <b>E- prefix</b>.
</p>

<p>
Example: the <b>RAX / EAX / AX / AL</b> hierarchy:
</p>

<pre style="background:#0d1117;padding:1rem;border-radius:8px;color:#c9d1d9;">
Byte number:
┌────┬────┬────┬────┬────┬────┬────┬────┐
│7th │6th │5th │4th │3rd │2nd │1st │0th │
├────────────────────────────────────────┤
│                RAX (64-bit)            │
├──────────────────────────────┬─────────┤
│          EAX (32-bit)        │         │
├────────────┬───────────────────────────┤
│    AX (16-bit)                         │
├────────────┬────────────┐              │
│   AH (8-bit) │  AL (8-bit)             │
└────────────┴────────────┴──────────────┘
</pre>

<p>
The <code>main()</code> function returns an <code>int</code>, and in C/C++ <code>int</code> is still 32-bit.  
Therefore the compiler zeroes <b>EAX</b> (the 32-bit subregister) rather than the whole <b>RAX</b> to preserve compatibility.
</p>

<p>
Also, the function allocates <b>40 bytes</b> on the stack. These 40 bytes are called the <b>shadow space</b> (explained later).
</p>

<hr>

<h2 style="color:#3ba2a6;"><b>GCC: x86-64</b></h2>

<p>
Now let’s try GCC on a 64-bit Linux system:
</p>

```assembly
Listing 1.23: GCC 4.4.6 x64
.string "hello, world\n"

main:
    sub     rsp, 8
    mov     edi, OFFSET FLAT:.LC0 ; "hello, world\n"
    xor     eax, eax ; number of vector registers passed
    call    printf
    xor     eax, eax
    add     rsp, 8
    ret
```

<p>
On Linux/BSD/macOS the calling convention also passes arguments in registers.  
According to the <b>System V ABI</b> (used by Unix-like systems), the first <b>six</b> arguments are passed in registers:
</p>

  <thead style="background:#9a3ba6; color:#fff;">
    <tr>

<p>
If there are more than six arguments the rest go on the stack as usual.
</p>

<p>
In the example above the pointer to the string is passed in <b>EDI</b> (the lower 32-bit part of <b>RDI</b>).
</p>

<p>
<b>Why EDI and not RDI?</b> — this is an optimization trick by the compiler:
</p>

<ul>
  <li>Writing to the 32-bit subregister (e.g., <b>EDI</b>) automatically clears the upper 32 bits of the full 64-bit register (<b>RDI</b>).</li>
  <li>This means a <code>mov edi, imm</code> instruction encodes smaller (5 bytes) than <code>mov rdi, imm64</code> (7 bytes), saving space in the binary.</li>
</ul>

<p>
Example machine code bytes (from the object file) show this size saving:
</p>

<p>
As you see, the instruction writing into <b>EDI</b> at 0x4004D4 is 5 bytes long; writing a full 64-bit immediate into <b>RDI</b> would be 7 bytes — GCC chooses the shorter encoding because it’s safe (string addresses are typically below 4GB in these examples) and saves space.
</p>

<p>
Also note that <b>EAX</b> is zeroed before the call to <code>printf()</code>. According to the calling convention, the number of vector registers used must be placed in <b>EAX</b> for Unix x86-64 calls.
</p>
