<img src="/src/content/assets/img/arm_arch.png" alt="arm_arch" style="display:block; margin:20px auto; border-radius:12px; max-width:60%;">
<p>
The author mentioned that in all the experiments we conducted on ARM, several compilers were used:
</p>

<ul>
  <li>The famous one in the Embedded Systems field: <b style = "color: crimson;">Keil version 6/2013</b>.</li>
  <li><b style = "color: crimson;">Apple Xcode 4.6.3 IDE</b> with the <b style = "color: crimson;">LLVM-GCC 4.2</b> compiler.</li>
  <li><b style = "color: crimson;">GCC 4.9 (Linaro)</b> (for ARM64 architectures)
  </li>
</ul>

<p>
In all the examples in this book, ARM 32-bit code is used (including Thumb and Thumb-2 modes), unless stated otherwise.
</p>

<p>
When we talk about ARM 64-bit, we call it <b>ARM64</b>.
</p>

<h2 style="color:#3ba2a6;"><b>Keil 6/2013 Without Optimization (in ARM Mode)</b></h2>


<p>
Let’s start compiling our example on Keil:
</p>



```terminal
armcc.exe --arm --c90 -O0 1.c
```

<p>
The <b>armcc</b> compiler outputs Assembly in <b>Intel Syntax</b>, 
but with ARM-specific macros. What matters more to us is to see the instructions exactly as they are, so let’s look at the result in <b>IDA</b>:
</p>



```assembly
.text:00000000                         main
.text:00000000 10 40 2D E9             STMFD             SP!, {R4,LR}
.text:00000004 1E 0E 8F E2             ADR               R0, aHelloWorld ; "hello, world"
.text:00000008 15 19 00 EB             BL                __2printf
.text:0000000C 00 00 A0 E3             MOV               R0, #0
.text:00000010 10 80 BD E8             LDMFD             SP!, {R4,PC}
.text:000001EC 68 65 6C 6C+aHelloWorld DCB "hello, world",0
```


<p>
In this example, we can easily see that each instruction is 4 bytes in size. This is because we compiled it in ARM mode, not Thumb.
</p>

<p>
The first instruction:
</p>


```assembly
STMFD SP!, {R4, LR}
```



<p>
This means:
</p>

<blockquote style="background:#2b2b2b; color:#ddd; padding:10px 14px; border-left:4px solid #9a3ba6; border-radius:6px;">
"Store Multiple Full Descending"<br><br>
1. The SP (Stack Pointer) is decreased enough to save the values.<br>
2. The values in R4 and LR are written into the Stack.<br><br>
It’s similar to the `PUSH` command in x86,<br><br>
but the difference is that here you can push multiple registers at the same time.
</blockquote>

<p>
But be careful, the armcc compiler outputs <b>PUSH {r4,lr}</b> for simplicity, but this is not accurate. The <b>PUSH</b> command is only available in <b>Thumb mode</b>.
</p>

<p>
That’s why in IDA we see it in the real form: <b>STMFD</b>.
</p>

<p>
The second instruction:
</p>


```assembly
ADR R0, aHelloWorld
```

<p>
This adds or subtracts the value in the PC (Program Counter) to get the offset for the string `"hello, world"`.
</p>

<p>
This is called <b>Position-Independent Code</b> (code that is not tied to a fixed address).
</p>

<p>
This code can be executed anywhere in memory because it relies on the difference (offset) between the code’s location and the data’s location.
</p>

<p>
This offset is calculated at runtime, so once we add the current instruction address (from PC), we can reach the actual address of our string.
</p>

<p>
The next instruction:
</p>



```assembly
BL __2printf
```


<p>
This makes a <b>call</b> to the `printf()` function, and here’s how it works:
</p>

<ul>
  <li>It saves the address after the <b>BL</b> (0xC) in the <b>LR</b> (Link Register).</li>
  <li>Then, it transfers control to the address of <b>printf()</b> by writing it into the <b>PC</b>.</li>
</ul>

<p>
When <b>printf()</b> finishes, it needs to return, and that’s done by the address stored in <b>LR</b>.
</p>

<p>
The difference here is that ARM processors (which are RISC) store the return address in <b>LR</b>, while x86 processors (CISC) place it on the stack.
</p>

<p>
The author will explain this in more detail in another section.
</p>

<p>
By the way, the <b>BL</b> instruction cannot store a full 32-bit address because it only has 24 bits for this space.
</p>

<p>
Since each instruction in ARM is 4 bytes (32-bit), it is placed on an address that is divisible by 4 (i.e., the last 2 bits are zero). These bits are ignored, leaving us with 26 bits to use as an offset.
</p>

<p>
This is enough to cover about ±32 MB around the current <b>PC</b>.
</p>

<p>
Afterwards, <b>MOV R0, #0</b> writes the value 0 into register <b>R0</b>.
</p>

<p>
This is because the <b>main</b> function returns 0 at the end, and this return value is stored in <b>R0</b>.
</p>

<p>
The final instruction:
</p>



```assembly
LDMFD SP!, {R4,PC}
```

<p>
This reads the values from the stack and stores them in <b>R4</b> and <b>PC</b>, then increments <b>SP</b> — essentially performing a <b>POP</b>.
</p>

<p>
Note:
</p>

<ul>
  <li>The first <b style = "color: springgreen;">STMFD</b> instruction stored (R4 and LR) on the stack.</li>
  <li>The <b style = "color: springgreen;">LDMFD</b> instruction returns (R4 and PC).</li>
</ul>

<p>
This is logical because initially, <b>LR</b> points to the return address from <b>printf</b>, and later it’s moved to <b>PC</b> to return control to the <b>main</b> caller.
</p>

<p>
After <b>main</b> finishes, the control is returned to the OS or CRT.
</p>

<p>
That’s why there’s no need to write <b>BX LR</b> at the end of the function.
</p>

<p>
Finally, <b>DCB</b> is a directive in assembly used to define an array of bytes or strings, similar to <b>DB</b> in x86 assembly.
</p>

<h2 style="color:#3ba2a6;"><b>Non-optimizing Keil 6/2013 (Thumb mode)</b></h2>

<p>
Let’s compile the same example, but this time in <b>Thumb mode</b>:
</p>


```terminal
armcc.exe --thumb --c90 -O0 1.c
```

<p>
The result in IDA looked like this:
</p>

```assembly
.text:00000000             main
.text:00000000 10 B5         PUSH        {R4,LR}
.text:00000002 C0 A0         ADR         R0, aHelloWorld ; "hello, world"
.text:00000004 06 F0 2E F9   BL          __2printf
.text:00000008 00 20         MOVS        R0, #0
.text:0000000A 10 BD         POP         {R4,PC}
.text:00000304 68 65 6C 6C+aHelloWorld DCB "hello, world",0
```

<p>
We can easily notice that the opcodes are all 2 bytes (16 bits) in size, which means this code is indeed in <b>Thumb mode</b>.
</p>

<p>
But keep in mind that the <b>BL</b> instruction here is composed of <b>two instructions</b> (each 16 bits), as it’s not possible to fit the full offset for <b>printf()</b> within a single 16-bit space.
</p>

<p>
Here’s what happens:
</p>

<ul>
  <li>The first 16 bits load the top 10 bits of the offset.</li>
  <li>The second instruction loads the lower 11 bits of the offset.</li>
</ul>

<p>
Since every Thumb instruction is 2 bytes, it means no instruction can be placed at an odd address. Therefore, the last bit of the address is discarded during encoding.
</p>

<p>
In the end, the <b>BL</b> in Thumb mode can encode an offset of around:
</p>

<blockquote style="background:#2b2b2b; color:#ddd; padding:10px 14px; border-left:4px solid #9a3ba6; border-radius:6px;">
current_PC ± approximately 2 MB.
</blockquote>

<p>
As for the other instructions in the example:
</p>

<ul>
  <li><b style = "color: springgreen;">PUSH / POP</b> work here just like <b style = "color: springgreen;">STMFD / LDMFD</b> we explained earlier,</li>
  <li>but the difference is that the <b>SP</b> is not explicitly remembered.</li>
  <li><b style = "color: springgreen;">ADR</b> does the same job.</li>
  <li><b style = "color: springgreen;">MOVS R0, #0</b> stores 0 in R0 so the function returns 0 at the end.</li>
</ul>

<h1 style="color:#9a3ba6;"><b>Optimizing Xcode 4.6.3 (LLVM) (ARM mode)</b></h1>

<p>
The author here used <b>Xcode 4.6.3</b>, but this time enabled <b>Optimization</b> (maximum level) using the switch:
</p>


```terminal
-O3
```
<p>
Without optimization, unnecessary code is generated, so the author opted for the version with the fewest possible instructions.
</p>


<h2 style="color:#3ba2a6;"><b>Listing 1.27: Optimizing Xcode 4.6.3 (LLVM) (ARM mode)</b></h2>


```assembly
__text:000028C4                       _hello_world
__text:000028C4 80 40 2D E9   STMFD    SP!, {R7,LR}
__text:000028C8 86 06 01 E3   MOV      R0, #0x1686
__text:000028CC 0D 70 A0 E1   MOV      R7, SP
__text:000028D0 00 00 40 E3   MOVT     R0, #0
__text:000028D4 00 00 8F E0   ADD      R0, PC, R0
__text:000028D8 C3 05 00 EB   BL       _puts
__text:000028DC 00 00 A0 E3   MOV      R0, #0
__text:000028E0 80 80 BD E8   LDMFD    SP!, {R7,PC}

__cstring:00003F62 48 65 6C 6C+aHelloWorld_0 DCB "Hello world!",0
```

<p>
The <b style = "color: springgreen;">STMFD</b> and <b style = "color: springgreen;">LDMFD</b> instructions are already familiar to us.
</p>

<p>
As for <b>MOV</b>, here it writes the value <b>0x1686</b> into <b>R0</b>, which is an offset pointing to the location of the string `"Hello world!"`.
</p>

<p>
The <b>R7</b> register (as mentioned in the iOS ABI Function Call Guide - 2010) is used as the <b>Frame Pointer</b> (which will be explained later).
</p>

<p>
The <b>MOVT R0, #0</b> (MOVe Top) writes zero into the upper 16 bits of the register.
</p>

<p>
Why?
</p>

<p>
In ARM mode, a regular <b>MOV</b> only writes to the lower 16 bits (the first 16 bits).
</p>

<p>
But if you want to write to the higher part of the register, you must use <b>MOVT</b>.
</p>

<p>
However, in this case, using <b>MOVT</b> was <b>unnecessary</b>, because the initial <b>MOV</b> already set the upper part to zero.
</p>

<p>
This is a small mistake from the compiler (an unnecessary addition).
</p>

<p>
Then:
</p>




```assembly
ADD R0, PC, R0
```
<p>
This adds the value of <b>PC</b> to <b>R0</b> to get the full address of the string.
</p>

<p>
This follows the same idea of <b>position-independent code</b> that we discussed earlier.
</p>

<p>
The <b>BL _puts</b> instruction calls the <b>puts()</b> function instead of <b>printf()</b>.
</p>

<p>
LLVM here replaced <b>printf</b> with <b>puts</b>, and this makes sense because <b>printf("Hello world!")</b> and <b>puts("Hello world!")</b> produce the same result as long as there are no format specifiers like <b>%d</b> or <b>%s</b>.
</p>

<p>
But if there is a <b>%</b>, the result will differ.
</p>

<p>
The reason for this replacement?
</p>

<p>
Because <b>puts is faster</b> — it simply prints the string without looking for format specifiers within it.
</p>

<p>
At the end:
</p>


```assembly
MOV R0, #0
```

<p>
This writes zero into <b>R0</b> as the return value.
</p>

<h2 style="color:#3ba2a6;"><b>Optimizing Xcode 4.6.3 (LLVM) (ARM mode) - Thumb-2 Mode</b></h2>

<p>
By default, Xcode 4.6.3 generates code for Thumb-2 in this manner:
</p>



```assembly
__text:00002B6C                 _hello_world
__text:00002B6C 80 B5           PUSH       {R7,LR}
__text:00002B6E 41 F2 D8 30     MOVW       R0, #0x13D8
__text:00002B72 6F 46           MOV        R7, SP
__text:00002B74 C0 F2 00 00     MOVT.W     R0, #0
__text:00002B78 78 44           ADD        R0, PC
__text:00002B7A 01 F0 38 EA     BLX        _puts
__text:00002B7E 00 20           MOVS       R0, #0
__text:00002B80 80 BD           POP        {R7,PC}

__cstring:00003E70 48 65 6C...  "Hello world!",0xA,0
```

<p>
In Thumb mode, the <b>BL</b> and <b>BLX</b> instructions are composed of <b>pairs of 16-bit instructions</b>.
</p>

<p>
However, in <b>Thumb-2</b>, these instructions were extended to allow <b>32-bit instructions</b>.
</p>

<p>
This is evident because Thumb-2 instructions always start with the code <b>0xFx or 0xEx</b>.
</p>

<p>
But in <b>IDA</b>, the byte order is reversed because ARM processors store bytes in reverse order:
</p>

<ul>
  <li>In ARM or ARM64 mode: Byte order is <b>4-3-2-1</b>.</li>
  <li>In Thumb mode: <b>2-1</b>.</li>
  <li>In a pair of 16-bit instructions in Thumb-2: <b>2-1-4-3</b>.</li>
</ul>

<p>
That’s why we see that instructions like <b>MOVW</b>, <b>MOVT.W</b>, and <b>BLX</b> all start with <b>0xFx</b>.
</p>

<p>
For example:
</p>



```assembly
MOVW R0, #0x13D8
```


<p>
This places a 16-bit value in the lower part of the <b>R0</b> register and zeroes out the upper bits.
</p>

<p>
Similarly, <b>MOVT.W R0, #0</b> works the same as the <b>MOVT</b> in the previous example, but it’s the Thumb-2 version.
</p>

<p>
The difference is that here we use <b>BLX</b> instead of <b>BL</b>.
</p>

<p>
The difference between them is that <b>BLX</b> not only transfers execution to the <b>puts()</b> function and stores the address in <b>LR</b>, but it also switches the <b>processor mode from Thumb or Thumb-2 to ARM</b> (or vice versa).
</p>

<p>
This instruction is here because the location where the code is going has the following code:
</p>



```assembly
__symbolstub1:00003FEC    _puts
__symbolstub1:00003FEC    44 F0 9F E5    LDR PC, =__imp__puts
```
<p>
This is simply a <b>jump</b> to the location where the <b>real address of the puts() function</b> is stored in the <b>import section</b>.
</p>

<p>
You might ask: “Why don’t we just call puts() directly instead of this roundabout way?”
</p>

<p>
The answer is that this method saves <b>space</b>.
</p>

<p>
Almost every program uses <b>dynamic libraries</b> (like DLLs in Windows, .so in Linux, or .dylib in macOS).
</p>

<p>
These libraries contain ready-made functions like <b>puts()</b>.
</p>

<p>
In the executable file (like EXE, ELF, or Mach-O), there’s an <b>import section</b>, which contains the names of the functions or variables that the program imports from other libraries, along with the name of the library they come from.
</p>

<p>
The <b>OS loader</b> reads this list and retrieves the real addresses of these functions from memory.
</p>

<p>
In our case, <b>__imp__puts</b> is a 32-bit variable that stores the address of the <b>puts()</b> function in memory.
</p>

<p>
Then, the <b>LDR</b> instruction reads this address and puts it in <b>PC</b> so execution transfers to the function.
</p>

<p>
That’s why instead of writing the address of <b>puts()</b> every time, we write it once in a designated place.
</p>

<p>
Also, it’s not possible to place the full 32-bit value into a register in a single instruction without touching memory.
</p>

<p>
So the optimal solution is to create a <b>small function in ARM mode</b> whose job is to <b>jump to the original function in the library</b>.
</p>

<p>
This is called a <b>Thunk Function</b>.
</p>

<p>
The code in Thumb mode calls this small function.
</p>

<p>
By the way, in the previous example (which was in ARM mode), the switch happens via a regular <b>BL</b> because the mode doesn’t change (that’s why the "X" is not in the name).
</p>

<h2 style="color:#9a3ba6;"><b>About Thunk Functions:</b></h2>

<p>
Many people get confused about <b>Thunk functions</b> because the name is strange.
</p>

<p>
But the idea is simple: a <b>Thunk</b> is an <b>adapter</b> or a <b>wrapper</b> between two different modes or systems.
</p>

<p>
That’s why sometimes they’re also called <b>Wrappers</b> (around another function).
</p>

<h3 style="color:#3ba2a6;"><b>Examples:</b></h3>

<ul>
  <li>According to researcher <b style = "color: darkgoldenrod;">P.Z. Ingerman</b>, who invented the Thunk in 1961, a thunk is "a piece of code that calculates a certain value and leaves the address of the result in a known place."</li>
  <li>Later, Microsoft and IBM also used the term when they made 16-bit and 32-bit systems work together (like WOW – Windows on Windows).</li>
  <li>For example, from the <b style = "color: darkgoldenrod;">LAPACK</b> library (used for linear algebra) written in FORTRAN, C/C++ developers love to use it, but it’s impossible to rewrite all the code. So they create small functions in C (thunks), and these functions call the original FORTRAN functions from within.</li>
</ul>

<p>
Example:
</p>


```assembly
double Blas_Dot_Prod(const LaVectorDouble &dx, const LaVectorDouble &dy){
    assert(dx.size() == dy.size());
    integer n = dx.size();
    integer incx = dx.inc(), incy = dy.inc();
    return F77NAME(ddot)(&n, &dx(0), &incx, &dy(0), &incy);
}
```

<p>
These small functions are also called <b>Wrappers</b>.
</p>

<h1 style="color:#9a3ba6;"><b>ARM64</b></h1>

<h2 style="color:#3ba2a6;"><b>GCC</b></h2>

<p>Let’s compile this example using <b>GCC 4.8.1</b> on the <b>ARM64 architecture</b>:</p>

```assembly
0000000000400590 main:
400590:   a9bf7bfd   stp    x29, x30, [sp,#-16]!
400594:   910003fd   mov    x29, sp
400598:   90000000   adrp   x0, 400000 _init-0x3b8
40059c:   91192000   add    x0, x0, #0x648
4005a0:   97ffffa0   bl     400420 puts@plt
4005a4:   52800000   mov    w0, #0x0
4005a8:   a8c17bfd   ldp    x29, x30, [sp],#16
4005ac:   d65f03c0   ret
```

<p>In the <b>.rodata</b> section (which contains the string data):</p>



```assembly
400640 01000200 00000000 48656c6c6f210a00 ........Hello!..
```

<p>In <b>ARM64</b>, there’s neither <b>Thumb</b> nor <b>Thumb-2 mode</b>, meaning everything is in <b>ARM mode</b> only, and all instructions are 32-bit in size.</p>

<p>The number of registers has doubled. The registers here are 64-bit and begin with <b>X</b>, whereas the lower part of them (32-bit only) is written with <b>W</b>.</p>

<p>The <b>STP (Store Pair)</b> instruction stores <b>two registers</b> at once in the stack: here <b>X29 and X30</b>, and of course, they can be stored anywhere in memory, but here it is written as <b>SP</b> (Stack Pointer). This means this pair is stored in the stack itself.</p>

<p>Since the register is 64-bit, each of them is 8 bytes, so together they occupy 16 bytes.</p>

<p>The exclamation mark <code>!</code> after the operand means that this value (16) is subtracted from SP first, and then the values are written to the stack — this is called <b>pre-index</b>. (This is the opposite of <b>post-index</b>, which increases SP afterward).</p>

<p>Comparing with x86, the first instruction here is essentially the same as:</p>



```assembly
PUSH X29
PUSH X30
```

<p><b>X29</b> is the <b>Frame Pointer (FP)</b>, and <b>X30</b> is the <b>Link Register (LR)</b>. These are stored at the beginning of the function (prologue) and restored at the end (epilogue).</p>

<p>The second instruction <code>mov x29, sp</code> copies the address of the Stack Pointer into <b>X29</b> to prepare the <b>stack frame</b> for the function.</p>

<p>Next, we have the <b>ADRP</b> and <b>ADD</b> instructions. Both are used to place the address of the string <code>"Hello!"</code> into register <b>X0</b> (because the first parameter of the function is passed in <b>X0</b>).</p>

<p>There’s no single ARM instruction that can place a large number or a full address into a register (because the instruction size is limited to 4 bytes).</p>

<p>Thus, it is done in two steps:</p>

<ul>
  <li><b style = "color: springgreen;">ADRP</b> places the address of the page (4KB Page) containing the string.</li>
  <li><b style = "color: springgreen;">ADD</b> adds the remaining part of the address.</li>
</ul>

<p>The resulting address:</p>



```assembly
0x400000 + 0x648 = 0x400648
```

<p>This is indeed the location of the string <code>"Hello!"</code> that we found in <b>.rodata</b>.</p>

<p>After that, <code>BL puts@plt</code> is used to call the <b>puts()</b> function (as we saw earlier).</p>

<p>Then <code>MOV W0, #0</code> places zero into register <b>W0</b>, which is the lower 32 bits of register <b>X0</b>:</p>




```ascii
High 32 bits | Low 32 bits
       X0
              |   W0
```

<p>The function returns a result in <b>X0</b>, and since <b>main()</b> returns an <code>int</code> (which is 32 bits), it’s sufficient to fill only the lower part <b>W0</b>.</p>

<p>To confirm, let’s modify the example to make it return a <code>uint64_t</code> (64 bits):</p>


```c/c++
include <stdio.h>
#include <stdint.h>

uint64_t main() {
    printf("Hello!"\n);
    return 0;
}
```


<p>You will get the same result, but now this instruction has become:</p>



```assembly
4005a4: d2800000  mov x0, #0x0
```


<p>This means that when the function returns 64 bits, the value must be written in <b>X0</b>, not <b>W0</b>.</p>

<p>Next, <code>LDP X29, X30, [SP], #16</code> reads the values we previously stored (X29 and X30) from the stack. But here there’s no exclamation mark — this means the values are pulled first, and then SP is increased by 16 (this is called <b>post-index</b>).</p>

<p>Finally, <code>RET</code> is a new instruction in ARM64. It performs the same job as <code>BX LR</code>, but with an extra bit that tells the processor this is a "return from function," not just a jump, making it execute faster.</p>

<p>Because the function is very simple, even in optimization mode (Optimized), GCC produces exactly the same code.</p>

<h1 style="color:#9a3ba6;"><b>MIPS</b></h1>
<img src="/src/content/assets/img/MIPS.png" alt="MIPS" style="display:block; margin:20px auto; border-radius:12px; max-width:60%;">

<p>
There is a very important concept in the <b>MIPS</b> architecture called the <b>“Global Pointer” (GP)</b>.
</p>

<p>
As we know, every <b>instruction</b> in MIPS is <b>32 bits</b> in size,
and that means it’s impossible to include a full <b>32-bit address</b> inside a single instruction.
</p>

<p>
That’s why we have to use <b>two instructions</b> to load the full address  
(just like what <b>GCC</b> did in the previous example when loading the address of a <b>text string</b>).
</p>

<p>
But we can load data from an address within the range  
from <b>register - 32768</b> up to <b>register + 32767</b> using only <b>one instruction</b>.
</p>

<p>
That’s because <b>16 bits</b> of <b>signed offset</b> can be encoded inside a single instruction.
</p>

<p>
So, we can dedicate a special <b>register</b> for this purpose,  
and also allocate a <b>64KiB</b> space that contains the most frequently used data.
</p>

<p>
This <b>register</b> is called the <b>“Global Pointer”</b>,  
and it points exactly to the middle of that <b>64KiB</b> space.
</p>

<p>
That space usually contains <b>global variables</b>  
and addresses of <b>ready-made functions</b> like <code>printf()</code>.
</p>

<p>
That’s because the <b>GCC</b> developers decided that getting the address of any <b>function</b>  
should take only <b>one instruction</b> instead of <b>two</b>.
</p>

<p>
In <b>ELF</b> files (which are the executable file format in Linux),  
this <b>64KiB</b> space is divided into two sections:
</p>

<ul>
  <li><b style = "color: crimson;" >.sbss</b> (“small BSS”) for <b>uninitialized data</b></li>
  <li><b style = "color: crimson;">.sdata</b> (“small data”) for <b>initialized data</b></li>
</ul>

<p>
This means the programmer can choose which data should be accessed quickly  
and place it either in <b>.sdata</b> or <b>.sbss</b> as needed.
</p>

<p>
Some old programmers might remember the <b>MS-DOS</b> system,  
which divided the entire memory into <b>64KiB blocks</b> —  
it’s basically the same idea here.
</p>

<p>
This concept isn’t exclusive to <b>MIPS</b>;  
at least the <b>PowerPC</b> architecture also used this same technique.
</p>

<h2 style="color:#3ba2a6;"><b>Optimizing GCC</b></h2>

<p>
Now let’s look at this example that explains the idea called the <b>“Global Pointer”</b> in the <b>MIPS</b> architecture.
</p>

<hr>

<h2 style="color:#3ba2a6;"><b>Listing 1.32: Optimizing GCC 4.4.5 (assembly output)</b></h2>

```assembly
1 $LC0:
2 ; \000 is zero byte in octal base:
3     .ascii "Hello, world!\012\000"
4 main:
5 ; function prologue.
6 ; set the GP:
7     lui              $28,%hi  __gnu_local_gp
8     addiu         $sp,$sp,-32
9     addiu         $28,$28,%lo __gnu_local_gp
10 ; save the RA to the local stack:
11    sw                $31,28($sp)
12 ; load the address of the puts() function from the GP to $25:
13    lw                  $25,%call16(puts)($28)
14 ; load the address of the text string to $4 ($a0):
15    lui                   $4,%hi($LC0)
16 ; jump to puts(), saving the return address in the link register:
17    jalr                    $25
18    addiu                $4,$4,%lo($LC0) ; branch delay slot
19 ; restore the RA:
20    lw                      $31,28($sp)
21 ; copy 0 from $zero to $v0:
22    move                 $2,$0
23 ; return by jumping to the RA:
24    j                          $31
25 ; function epilogue:
26    addiu                   $sp,$sp,32 ; branch delay slot + free local stack
```

<p>
The interesting part here is that <b>IDA</b> recognized that the two instructions <code>LUI</code> and <code>ADDIU</code> together  
actually perform a <b>Load Address</b> operation,  
so it combined them into a single pseudo-instruction called <code>LA</code>.
</p>

<p>
This isn’t a real instruction in <b>MIPS</b>, but a <b>pseudo-instruction</b> representing both combined.
</p>

<p>
The <code>LA</code> instruction occupies <b>8 bytes</b>, since it is actually composed of two real instructions.
</p>

<p>
Also, <b>IDA</b> doesn’t display <b>NOPs</b> as <code>NOP</code>,  
so they appear as <code>OR $AT, $ZERO</code>.
</p>

<p>

so the result remains unchanged, effectively doing nothing.
</p>

<p>
Like several other architectures, <b>MIPS</b> doesn’t have a real <b>NOP</b> instruction,  
so it uses an <b>OR</b> operation like this as a replacement.
</p>

<h3 style="color:#9a3ba6;"><b>The Role of the Stack Frame in This Example</b></h3>

<p>
The text string’s address is passed through a register —  
so why do we even need a local stack?
</p>

<p>
The reason is that the values of <b>RA</b> and <b>GP</b> must be stored somewhere  
before calling <code>printf()</code> (or <code>puts()</code> in this case),  
because the call might modify them.
</p>

<p>
So, we use the <b>stack</b> to save them.
</p>

<p>
If this function were a <b>leaf function</b> (meaning it doesn’t call any other functions),  
we could skip the entire <b>prologue</b> and <b>epilogue</b> altogether.
</p>

<h2 style= "color:#3ba2a6;"><b>1.5.5 Summary:</b></h2>

<p>The main difference between <b>x86/ARM</b> and <b>x64/ARM64</b> code is that the pointer that points to the string became 64-bit instead of 32-bit.</p>

<p>This is because modern processors have become 64-bit, since memory is now cheaper and programs require more of it.</p>

<p>As a result, computers today can install much more memory than what 32-bit pointers could address.</p>

<p>Therefore, all pointers are now 64-bit.</p>
