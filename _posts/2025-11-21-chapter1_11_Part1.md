<code>
    push 3
    push 2
    push 1
    push OFFSET $SG3830
</code>
</pre>
</div>

<p>
I will explain this simply.
</p>

<p>
Here <code style = "color: chartreuse;">printf</code> needs <b>4</b> arguments, which are:
</p>

<ol>
  <li style = "color: chocolate;"><b>The address of the string</b></li>
  <li style = "color: chocolate;"><b>Number 1</b></li>
  <li style = "color: chocolate;"><b>Number 2</b></li>
  <li style = "color: chocolate;"><b>Number 3</b></li>
</ol>

<p>
But of course, as we discussed earlier, it pushes in reverse — meaning it starts pushing number <b>3</b> up to pushing the address of the string.
</p>

<p>
So the actual order will look like this:
</p>

<pre style="padding:1rem;background:#0d1117;color:#c9d1d9;border-radius:8px;">
3
2
1
address_of_string
</pre>

<p>
By the way, variables of type <code style = "color: chartreuse;">int</code> in a 32-bit environment are 32-bit in size, i.e., 4 bytes.
</p>

<p>
So we have 4 arguments here.
<br>
4 × 4 = 16 — and that is exactly the size they occupy on the 32-bit stack (the string pointer + 3 ints).
</p>

<p>
After the function finishes, the stack must be cleaned up (stack cleanup).
</p>

<p>
So we use:
</p>

<p><code style = "color: chartreuse;">add esp, 16</code></p>

<p>
This means, as we saw above, the function had 16 bytes of arguments.
</p>

<p>
If you divide them by 4, you get the number of arguments:
</p>

<pre style="padding:1rem;background:#0d1117;color:#c9d1d9;border-radius:8px;">
16 / 4 = 4 arguments
</pre>

<p>
Of course this applies only to a calling convention named <b style = "color: chocolate;">cdecl</b> and also only in a 32-bit environment.
</p>

<p>
The author said something very important which is:
</p>

<p>
If there are several calls one after another:
</p>

<pre style="padding:1rem;background:#0d1117;color:#c9d1d9;border-radius:8px;">
call A  (1 arg)
call B  (0 arg)
call C  (3 args)
</pre>

<p>
Instead of doing:
</p>

<pre style="padding:1rem;background:#0d1117;color:#c9d1d9;border-radius:8px;">
add esp,4
add esp,0
add esp,12
</pre>

<p>
It will add them all together into:
</p>

<pre style="padding:1rem;background:#0d1117;color:#c9d1d9;border-radius:8px;">
add esp, 16
</pre>

<p>
Which is faster and better.
</p>

<p>
And here is a real-life example:
</p>

<pre style="padding:1rem;background:#0d1117;color:#c9d1d9;border-radius:8px;">
push 3
call sub_100018B0 ; takes one argument (3)

call sub_100019D0 ; takes no arguments

call sub_10006A90 ; takes no arguments

push 1
call sub_100018B0 ; takes one argument (1)

add esp, 8 ; removes two arguments that were on the stack
</pre>

<p>
GDB shows that printf() returned the value <b>13</b> in EAX.
</p>

<p>
This is the number of characters that were printed… like the OllyDbg example.
</p>

</p>

<p>
Indeed the file exists in the current directory, and GDB found this line in it.
</p>

<p>
How does GDB know which C line is being executed?
</p>

<p>
Because the compiler, while generating the debugging info, stores a <b>mapping table</b> between the source code lines and the instruction addresses.
</p>

<p>
GDB is a source-level debugger.
</p>

<h1 style="color:#9a3ba6;"><b>MSCV</b></h1>


<hr>
<img src="/assets/img/MSCV.png" alt="MSCV" style="display:block; margin:20px auto; border-radius:12px; max-width:60%;">

<p>
<br>
As we said before, the first 4 arguments must be sent via the RCX, RDX, R8, R9 registers in Win64 and the remainder is passed via the stack — and this is exactly what we see here. But the <code style="color: chartreuse;">MOV</code> instruction, instead of <code style="color: chartreuse;">PUSH</code>, is used to prepare the stack, so the values are stored directly on the stack.
</p>

    sub  rsp, 88                    ; Allocate 88 bytes on stack (shadow space + locals)
    mov  DWORD PTR [rsp+64], 8      ; Store integer 8 at [rsp+64] (argument passed on stack)
    mov  DWORD PTR [rsp+56], 7      ; Store integer 7 at [rsp+56]
    mov  DWORD PTR [rsp+48], 6      ; Store integer 6 at [rsp+48]
    mov  DWORD PTR [rsp+40], 5      ; Store integer 5 at [rsp+40]
    mov  DWORD PTR [rsp+32], 4      ; Store integer 4 at [rsp+32]
    mov  r9d, 3                     ; Place value 3 into r9d (register argument)
    mov  r8d, 2                     ; Place value 2 into r8d (register argument)
    mov  edx, 1                     ; Place value 1 into edx (register argument)
    lea  rcx, OFFSET FLAT:$SG2923   ; Load effective address of the format string into rcx (1st arg)

    ; return 0

<p>
The question now: why are 8 bytes allocated for <code style="color: chartreuse;">int</code> values even though 4 bytes are enough?
</p>

<p>
Yes, we must remember: 8 bytes are allocated for any data type smaller than 64-bit. This is done for convenience: it makes calculating the address of any argument easy.  
Also, they are all stored at properly aligned memory addresses (aligned).  
The same applies in a 32-bit environment: 4 bytes are reserved for each data type.
</p>

<h2 style="color:#3ba2a6;"><b>GCC</b></h2>

<p>
