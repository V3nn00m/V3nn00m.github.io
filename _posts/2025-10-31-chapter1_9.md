<h1 style="color:#9a3ba6;"><b>Stack</b></h1>

<hr>

<p>
The author said at first that the <b>Stack</b> is considered one of the most important data structures in computer science.
</p>

<p>
It is also known by something called <b style = "color: #058df1">LIFO (Last In, First Out)</b> — the last thing that enters is the first thing that comes out.
</p>

<p>
Now, technically, it is known that it is considered a part or a piece of memory inside the <b>process memory</b>.
</p>

<p>
It comes with the <b style = "color: #bbdf00">ESP</b> register in x86, <b style = "color: #bbdf00">RSP</b> in x64, and <b style = "color: #bbdf00">SP</b> in ARM.
</p>

<p>
Of course, as we said before, they act as pointers within a part of the memory.
</p>

<p>
The author also said that the most used instructions to access the stack are <b>PUSH</b> and <b>POP</b> (in x86, and also in ARM in Thumb mode).
</p>

<p>
<b>PUSH</b> subtracts from the <b>ESP/RSP/SP</b> 4 bytes in x86, and in x64 it subtracts 8 bytes, usually putting them in a register, then adds 4 or 8 to the Stack Pointer.
</p>

<p>
<b>POP</b> is the opposite operation: it takes the data from the memory location that the <b>SP</b> points to, puts it into the operand of the instruction (usually a register), and then adds 4 (or 8) to the Stack Pointer.
</p>

<h2 style="color:#3ba2a6;"><b>ARM Architecture</b></h2>

<p>
ARM supports both descending and ascending stacks.
</p>

<p>
For example, the instructions <b style = "color: #884e03ff">STMFD/LDMFD</b> and <b style = "color: #884e03ff">STMED/LDMED</b> are designed to work with a descending stack (grows downwards, starts from a high address and moves to a lower address).
</p>

<p>
The instructions <b style = "color: #884e03ff">STMFA/LDMFA</b> and <b style = "color: #884e03ff">STMEA/LDMEA</b> are designed for an ascending stack (grows upwards, starts from a low address and moves to a higher address).
</p>

<hr>

<h2 style="color:#3ba2a6;"><b>Why does the stack grow backwards?</b></h2>

<img src="/assets/img/Why does the stack grow backwards.png" alt="Why does the stack grow backwards" style="display:block; margin:20px auto; border-radius:12px; max-width:60%;">
<p>
The author explained that if you imagine memory as a number line, you would think that every time you add data to the <b>Stack</b> the address would increase (move right or up). That’s a natural expectation but it’s not what usually happens.
</p>

<p>
This is because the <b>Stack</b> grows in the opposite direction — not some deep scientific law, but it has a historical reason from the early days of computers.
</p>

<p>
Long ago computers were large and RAM was very small, so they simply divided memory into two regions: one for the <b>heap</b> and one for the <b>stack</b>.
</p>

<p>
Of course no one knew in advance how large the heap or the stack would be at runtime, so that split was the simplest possible solution.
</p>

<p>
A process’s memory is usually divided logically into three areas (segments).
</p>

<p>
The <b>code</b> segment (the program itself) usually starts from the first virtual address (address zero).
</p>

<p>
At runtime this segment is write-protected and a single copy of it is shared among all processes running the same program. Immediately after this segment (roughly 8K bytes after it) in the virtual address space the writable <b>data</b> segment begins; it is not shared and its size can grow via system calls.
</p>

<p>
Starting from the highest address in the virtual address space you find the <b>stack</b> segment, which automatically grows downward according to the hardware <b>stack pointer</b> movements.
</p>

<p>
The author then said this discussion reminds him of some students who write two lectures in one notebook.
</p>

<p>
Notes for the first lecture are written normally from the start, and notes for the second lecture are written from the back of the notebook, flipping pages in reverse.
</p>

<p>
If both write a lot, the notes may meet in the middle and the space runs out.
</p>

<hr>

<h2 style="color:#3ba2a6;"><b>What is the stack used for?</b></h2>

<p>
The author then said that the <b>Stack</b> is used to store the return address that a function should go back to after it finishes.
</p>

<p>
When you call another function with the <b>CALL</b> instruction, the address immediately after the <b>CALL</b> is stored on the stack, and then an unconditional jump to the address in the <b>CALL</b> occurs.
</p>

<p>
A <b>CALL</b> instruction is equivalent to doing a <b>PUSH</b> of the address after the <b>CALL</b> and then <b>JMP</b> to the function’s address.
</p>

<p>
A <b>RET</b> pulls a value from the stack and jumps to it — like doing <code>POP tmp</code> and then <code>JMP tmp</code>.
</p>

<h1 style="color:#9a3ba6;"><b>ARM</b></h1>

<hr>

<p>
The author said that ARM also uses the stack to store return addresses, but it does it in a slightly different way from x86.
</p>

<p>
And we have already said before that in ARM, the address that the function should return to after finishing is not always placed on the stack — it’s placed in a <b style="color:chartreuse;">register called LR (link register)</b>.
</p>

<p>
Let’s simplify things a bit:
</p>

<ul>
<li>If the function <b>does not</b> call any other functions → it can work without touching the stack at all (<b>leaf function</b>), LR stays fixed and there’s no need to save it.</li>

<li>If the function <b>will call</b> another function → when it executes <b>BL</b> inside it, LR will change (it will store the return address of the new function). So, if you want to return later to your original place, you must save LR before calling.</li>
</ul>

<p>
And usually, it’s saved in the <b>prologue</b>.
</p>

<h2 style="color:#3ba2a6;"><b>Local variable storage</b></h2>

<p>
A function can allocate space in the stack for local variables
simply by decreasing the value of the <b>Stack Pointer (ESP or RSP)</b>.
</p>

<p>
And this operation is extremely fast regardless of the number of variables.
</p>

<p>
Also, it’s not mandatory to store local variables in the stack;
you can store them anywhere else.
</p>

<p>
But by habit and programming convention, the <b>stack</b> is what’s usually used.
</p>

<hr>

<h2 style="color:#3ba2a6;"><b>x86: alloca() function</b></h2>

<p>
First of all, the <b>alloca()</b> function allocates <b>n bytes</b> on the <b>stack</b> instead of the heap and returns a pointer to the allocated block.
</p>

<p>
It works like <code>malloc</code>, but the storage location is different.
</p>

<p>
You don’t need to call <code>free()</code> for the memory allocated with <code>alloca</code>.  
Why? Because when the function that called <code>alloca</code> finishes, the <b>epilogue</b> restores <b>ESP</b> to its original position — meaning that the space allocated is “discarded” and becomes unavailable afterward.
</p>

<p>
And of course, it’s faster than <code>malloc</code> because it operates directly on the stack.
</p>

<p>
The code is identical to the Intel version, except for the syntax — in AT&amp;T, addresses use the form <code>offset(%reg)</code> instead of <code>[reg+offset]</code>.
</p>

<p>

</p>

<p>
Function arguments are also automatically released at the end of the function.  
In contrast, anything allocated on the heap must be explicitly freed using <code>free()</code>.
</p>

<h3 style="color:#3ba2a6;"><b>Stack state visualization</b></h3>

<p>Before any function executes:</p>

<pre style="background:#0d1117;border:1px solid #30363d;color:#c9d1d9;padding:1rem;border-radius:8px;">
ESP → empty
</pre>

<h4 style="color:#9a3ba6;">When <b>f1()</b> runs:</h4>

<pre style="background:#0d1117;border:1px solid #30363d;color:#c9d1d9;padding:1rem;border-radius:8px;">
ESP-4  → c = 3
ESP-8  → b = 2
ESP-12 → a = 1
</pre>

<h4 style="color:#9a3ba6;">When <b>f2()</b> runs:</h4>

<pre style="background:#0d1117;border:1px solid #30363d;color:#c9d1d9;padding:1rem;border-radius:8px;">
ESP-4  → c (uninitialized, actually still has value 3)
ESP-8  → b (uninitialized, still has value 2)
ESP-12 → a (uninitialized, still has value 1)
</pre>

<blockquote style="border-left:4px solid #3ba2a6;padding-left:1rem;color:#c9d1d9;">
See? <b>f2</b>’s variables still point to the same stack space as <b>f1</b>’s — that’s why the old values appear again.
</blockquote>
