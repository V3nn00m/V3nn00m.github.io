<p>
Nothing very strange, just two loops: the first loop fills the array (multiplying each element by 2), and the second loop prints the elements. But let's analyze the Assembly together a bit more for better understanding.
</p>
<p>
Imagine you have 20 drawers in a cabinet, all next to each other, and each drawer holds one number of type int. Therefore each drawer takes 4 bytes (because we said before that int in 32-bit takes 4 bytes), meaning the entire array takes 20 × 4 = 80 contiguous bytes.
</p>
<p>
Let's start with the instruction <code style="color:chartreuse;">sub esp, 84</code> which allocates 84 bytes on the stack. Why 84 and not 80? In short, there are 4 extra bytes for the variable <code style="color:chartreuse;">i</code>.
</p>
<p>
Now let's go through the first loop — filling the array:
</p>
<p>* <code style="color:chartreuse;">mov _i$, 0</code> — as we know, start with i = 0</p>
<p>* <code style="color:chartreuse;">cmp _i$, 20</code> — if i is greater than or equal to 20, exit the loop</p>
<p>* <code style="color:chartreuse;">shl ecx, 1</code> — the fastest way to multiply i × 2 (instead of a regular multiply, a left shift by 1 bit = ×2)</p>
<p>* calculating the address of a[i]: <code style="color:chartreuse;">mov DWORD PTR _a$[ebp + edx*4], ecx</code></p>
<p>
An important question — why did the compiler use <code style="color:chartreuse;">shl</code> instead of <code style="color:chartreuse;">imul</code>? Because it is safer on the stack (no overflow if the array is small).
</p>
<p>
Let's try this example in x32dbg. We can see how the array is being filled: each element is a 32-bit int word and its value is the index multiplied by 2.
</p>
<img src="/assets/x32dbg2/array_1.png" alt="array_1" style="display:block; margin:20px auto; border-radius:12px; max-width:80%;">
<p>
Since this array lives on the stack, we can see all 20 of its elements there.
</p>

<p>
By the way, the variable a is of type int (a pointer to int). You can pass a pointer to an array to another function, but it is more accurate to say "a pointer to the first element of the array is being passed" (and the rest of the addresses are calculated in a straightforward way). If you do indexing on this pointer like a[idx], idx is just added to the pointer and the element at that address is returned.
</p>
<p>
An interesting example: a string like "string" is an array of characters of type <code style="color:chartreuse;">const char[]</code>. You can do indexing on this pointer too. That is why it is possible to write <code style="color:chartreuse;">"string"[i]</code> and that is a completely valid expression in C/C++!
</p>

<p>
The int type takes 32 bits (4 bytes), so 20 elements need 80 bytes (0x50). The <code style="color:chartreuse;">SUB SP, SP, #0x50</code> instruction at the beginning of the function allocates exactly that space.
</p>
<p>
In both loops, the counter i lives in R4. The number written into the array = i*2, and this is translated into <code style="color:chartreuse;">MOV R0, R4,LSL#1</code> (left shift by 1 bit = multiply by 2). <code style="color:chartreuse;">STR R0, [SP,R4,LSL#2]</code> writes to the array. The element address = SP (start of array) + R4*4 (because each element is 4 bytes).
</p>

</p>

</p>

It is not easy in practice, but that is the core idea.
</p>

<h1 style="color:#9a3ba6; font-family: 'Press Start 2P', 'system-ui'"><b>1.26.3 Buffer overflow protection methods</b></h1>
<img src="/assets/img/Bufferoverflowprotectionmethods.jpeg" alt="overflow_1" style="display:block; margin:20px auto; border-radius:12px; max-width:80%;">

<hr>
 
<p>
Let's talk about ways to protect against buffer overflow even if the C/C++ programmer is not paying attention.
</p>
<p>
<b style="color:cornflowerblue;">MSVC</b> has options like these:
</p>
<p>* <code style="color:chartreuse;">/RTCs</code> → Stack Frame runtime checking</p>
<p>* <code style="color:chartreuse;">/GZ</code> → Enable stack checks (same as /RTCs)</p>
<p>
One of the methods is that it writes a <b style="color:cornflowerblue;">random value</b> between the local variables on the stack at the beginning of the function (prologue), and then checks it at the end of the function (epilogue) before exiting.
</p>
<p>
For example, if that value changed → do not execute the last RET instruction, but instead stop the program (or suspend it). The program will stop, but that is much better than someone attacking your machine remotely.
</p>
<p>
This random value is called a <b style="color:cornflowerblue;">"Canary"</b>, and this is connected to the canaries that mine workers used in the old days. They used canaries to detect toxic gases quickly. The canary is very sensitive to gases — if there is danger it becomes very distressed or dies.
</p>
<p>
If we compile the first example with the <code style="color:chartreuse;">/RTC1</code> and <code style="color:chartreuse;">/RTCs</code> options, we will find at the end of the function a call to the function <code style="color:chartreuse;">@_RTC_CheckStackVars@8</code> which checks that the "canary" is still intact.
</p>
<p>
Now let's see how it is done in GCC:
</p>
